# 音视频回放：抓包来源标注与排序规则

> 变更位置：`web/templates/results.html`（回放区 `showMedia` / `_mediaItem`，新增常量 `CAPTURE_SOURCE_NAMES`）
> 适用版本：基于"音视频回放按链路方向分组展示"的既有功能之上。

## 一、背景与要解决的问题

分析时可以同时上传最多三份抓包：**主叫侧（终端）、服务端（FS）、被叫侧（坐席）**。

后端重建媒体的基本单位是 **(SSRC, 抓包文件)**——同一条 RTP 流只要在某份抓包里出现过，就会从那份抓包里独立重建一段音/视频（`src/analyzer/media_extractor.py` 的 `generate_media_files`，manifest 每个条目自带 `role` 字段标记来源抓包）。因此三份抓包都上传时，回放区里同一条流的音频最多会出现三段。

**问题**：回放卡片此前只标注了媒体流向（如"主叫 → 服务端"）和收发方向（呼入/呼出），没有标注这段音/视频**取自哪份抓包**；多段音频之间的排列顺序也不受控。听感对比时分不清哪段是哪端抓到的。

## 二、功能一：抓包来源徽章

每张播放器卡片头部、紧跟在流向徽章之后，新增一个"来源"徽章：

| manifest 条目 role | 徽章文案 |
|---|---|
| `fs` | 来源：服务端抓包 |
| `terminal` | 来源：主叫侧抓包 |
| `seat` | 来源：被叫侧抓包 |
| 其他/缺失 | 显示原始角色名或不显示 |

- 徽章悬停提示："此音/视频从该份上传的抓包中重建"。
- 角色名与上传页三个抓包框（主叫端/服务端/被叫端）的措辞对应，未知角色回退显示原始 `role`。
- 回放区顶部的拓扑说明行同步更新为："每条媒体流的收发双方与抓包来源标注在各流开头"。

## 三、功能二：同一方向卡内的播放卡片排序

回放区按**链路方向**分组（如"主叫 → 被叫"、"被叫 → 主叫"，每张方向卡带无声诊断/延迟链路结论），方向卡之间的顺序不变（"主叫 → 被叫"在前）。本次新增的是**每张方向卡内部**各播放卡片的排序规则：

1. **服务端抓包的段全部排最前**——服务端抓包点能看到整条链路，是最完整的参照。
2. **服务端抓包内部的两条腿按三段式链路顺序**：收的腿（上游，如 主叫→FS）在前，发的腿（下游，如 FS→被叫）在后。
3. **其余段（主叫侧/被叫侧抓包）按三段式链路位置排**：上游腿（说话方 → 服务端）在前，下游腿（服务端 → 收听方）在后——不再按抓包来源固定排序。判断方式是拿抓包角色对照方向卡的说话方/收听方：
   - 抓包角色对上本卡**说话方** → 该段是上游腿（如"主叫 → 被叫"卡里主叫侧抓包的段、"被叫 → 主叫"卡里被叫侧抓包的段）；
   - 对上**收听方** → 下游腿；
   - 服务端抓包即规则 2；角色对不上时兜底"发送端视为上游腿"。
4. 同来源同腿位置再按 **SSRC** 稳定排序。

点对点通话（媒体不经服务端）时没有服务端抓包，退化为"说话方侧抓包在前、收听方侧抓包在后"，同样符合链路顺序。

## 四、效果示例

三份抓包都上传、单通经 FS 转发的通话，"主叫 → 被叫"方向卡内卡片顺序：

```
1. 来源：服务端抓包   主叫 → 服务端   （上游腿）
2. 来源：服务端抓包   服务端 → 被叫   （下游腿）
3. 来源：主叫侧抓包   主叫 → 服务端   （上游腿）
4. 来源：被叫侧抓包   服务端 → 被叫   （下游腿）
```

反方向"被叫 → 主叫"卡内同理，顺序随链路翻转（被叫侧抓包的段是上游腿，排在前）。

## 五、依赖的后端行为

- `generate_media_files`（`src/analyzer/media_extractor.py`）：按 (SSRC, 抓包) 逐份重建媒体，manifest 条目含 `role`、`direction`、`ssrc`、`flow` 字段——本功能完全基于这些既有字段，后端无需改动。
- `describe_media_parties`：为每条流标注真实收发双方（`flow.from/to`）与拓扑（`parties`），是方向分组和链路位置判断的依据。

## 六、边界与注意点

- 同一条流在某份抓包里出现多次或缺失时，只影响该来源的段数，不影响排序规则。
- 未能重建的流（`unsupported`）列表一直展示来源角色，不在本次改动范围。
- 方向卡归组失败退化为"其他流/FS 转发"组时，排序规则同样生效（服务端段在前，其余按链路位置/SSRC）。
