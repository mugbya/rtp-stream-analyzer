# RTP Stream Analyzer

VoIP 通话 RTP 音视频流分析平台。上传抓包文件（pcap/pcapng），自动检测**通话数量与抓包完整性**，分析**延迟、抖动、丢包**，并从 RTP 流**重建音频/视频供回放**。

## 功能

### 1. 通话检测与完整性标注
服务端抓包往往同时包含多通通话，分析前先自动分组：
- **通话分组**：按双向端口对构建媒体腿，时间重叠 + 共享 IP 聚类成通话；跨抓包文件按相同 SSRC 合并
- **完整性判断**（每通通话 × 每个抓包文件独立判断，附判断依据）：

| 状态 | 含义 |
|---|---|
| ✅ 完整 | 通话首尾都在抓包内（依据：INVITE 早于媒体开始 / BYE 晚于媒体结束 / 上行流首包 seq≈0） |
| ⚠️ 缺开头 | 开始抓包时通话已在进行（抓到一半） |
| ⚠️ 缺结尾 | 抓包结束时通话尚未挂断 |
| ❌ 首尾都不完整 | 抓包窗口完全落在通话中间 |

- 分析时**按通话过滤**：多通通话时选择具体通话再分析，避免不同通话的延迟/抖动混在一起失真（默认自动选中唯一通话；也可选"全部混合"，页面会提示风险）
- **跨抓包一致性检查（传错文件提醒）**：同一次通话的 SSRC 在每个抓包点相同、会被合并进同一通，因此坐席/FS/终端几份抓包至少应共享一通通话。若某两个角色之间找不到任何共同通话，判定为"可能传错了文件"，上传结果页与结果报告页都会显示黄色提醒（列出每个角色各自检测到的通话），并且此时**不再提供"全部混合"选项**、默认选中覆盖抓包最多的那通，引导用户以其中一通为准单独分析
- 判断依据引用 SIP 信令（INVITE/BYE 时间点）、上行流首包序列号、媒体起止与抓包边界的距离
- **信令按 Call-ID 唯一归属**：每个 Call-ID 会话组只挂到时间重叠最大的一通通话，同设备对背靠背的多次通话互不串扰（信令流程与完整性判断——INVITE/BYE 依据——都只看本通话自己的会话）
- **SIP 信令流程时序图（阶梯图）**：每通通话渲染为信令阶梯图，只保留「谁打给谁」的核心对话（识别结果页和结果报告页均可展开查看）；**通话卡片头部同样直接展示「主叫 → FS → 被叫」链路**，与阶梯图列头身份一致
  - 参与方为竖列：**经服务器 = 左（主叫）/ 中（FS 服务器）/ 右（被叫）；点对点呼叫 = 左右两列**。主叫/被叫自动标注徽章（主叫 = 第一个非服务器侧 INVITE 的发送方；被叫 = INVITE 事务 200 OK 的发送方，按 CSeq 归属判定，不受 CANCEL/BYE 的 200 干扰）；并发振铃的分叉目标等无关参与方及其消息不展示
  - **列头显示设备身份**：主叫取其自己 INVITE 的 From（自报账号/显示名），被叫取呼向它的 INVITE 的 To（被叫分机号——被叫响应里的 From 会按 RFC 3261 回显主叫身份，不能用于识别被叫）；无 SIP 身份信息时回退显示 IP，IP 始终保留在副行，长标识悬停可见全文
  - 按 Call-ID 从各抓包中提取 INVITE/ACK/BYE/CANCEL 等会话内消息，跨抓包去重（利用 CSeq 区分重传与认证重试，过滤 REGISTER/OPTIONS 保活噪声）。**多抓包副本按信令源优先级只保留一份**（FS 端 > 终端 > 坐席端）：FS 单一时钟、两侧都可见，整条时间线出自同一台机器，避免多机器时钟偏差导致消息排错序；同一 CSeq 的重传（间隔可达数十秒）也会被去重
  - 每条消息为带箭头横线，箭头指向接收方，线上标注时间与消息类型，按类型着色：请求=蓝、1xx=灰、2xx=绿、3xx~6xx=红
  - **RTP 媒体区间标线（接通后）**：两条标线**锚定在信令行上**——绿色开始线紧跟被叫应答的 200 OK 行之后，灰色结束线落在首条 BYE 行之前，保证两条线之间不夹应答/挂断握手的其余信令；线上标注媒体起止时间与持续时长。FS 从主叫一呼叫就可能开始收录 RTP（含振铃音/早期媒体），时间标注专指**双方接通后真正交换媒体**的区间（answer→bye 窗口内的 RTP 首末包）；无信令时回退为整段媒体首末包
  - **编码标签**：开始线下方（RTP 区间内）显示该通话实际使用的音频/视频编码——由 RTP 流真实出现的载荷类型（PT）反查：静态 PT（如 0=PCMU）用内置名称，动态 PT（96~127，如 H264）用 SDP rtpmap 解析；DTMF 事件流（telephone-event）不算媒体编码；动态 PT 连 SDP 都未抓到时标注 PT 号并说明
  - 可直观还原呼叫过程：应答、407 认证重试、re-INVITE、挂断双向 BYE 等

### 2. 延迟 / 抖动 / 丢包分析
- **FS 内部处理延迟**：在 FS 抓包中匹配入站/出站 SSRC 对，测量转发耗时
- **跨抓包传输延迟**：同一 SSRC 在不同抓包点的到达时间差（自动修正抓包机器间的时钟偏移）
- **端到端延迟估算**：FS 延迟 + 网络传输
- **抖动分析**：包间隔稳定性（均值/中位数/标准差/P95/P99/异常间隔）
- **丢包检测**：基于 RTP 序列号连续性
- 生成 9 面板分析图表 + 结构化结论报告（含问题分级与根因建议）

### 3. 音视频重建与回放
- **音频**：从 RTP 载荷重建 G.711 PCMU（μ-law）/ PCMA（A-law）为 WAV 文件
  - 按序列号排序，丢包位置自动补静音
  - 按抓包文件（坐席/FS/终端）分组，区分**呼出（该端发送）**与**呼入（该端接收）**
  - 每条流标注**收发双方（谁到谁）**：从通话 SIP 信令识别主叫/被叫（分机号/显示名），结合流的实际收发 IP 生成「主叫 张三（1001）→ FS」式标注；无信令时退化为抓包角色名或 IP。回放区开头附一句通话拓扑（主叫 ↔ FS ↔ 被叫，含 IP）
- **视频**：H.264 流去分片（FU-A/STAP-A，RFC 6184）导出裸流，调用 ffmpeg 转换为 MP4
- 网页内直接播放 / 下载

### 4. 自适应抓包数量
支持上传 1~3 个抓包文件（坐席端 / FS 端 / 终端端任意组合），系统自动识别可用分析项：

| 上传组合 | 可用分析 |
|---|---|
| 单端 | 抖动 + 丢包 |
| 坐席 + FS | 坐席↔FS 传输延迟 + FS 内部延迟 |
| FS + 终端 | FS↔终端 传输延迟 + FS 内部延迟 |
| 三端齐全 | 端到端延迟 + 全部分析项 |

## 环境要求

- Python 3.8+（开发环境为 3.11）
- **ffmpeg**（可选，视频转 MP4 需要）：`brew install ffmpeg`
- 其余依赖见 `requirements.txt`

## 安装

```bash
cd rtp-stream-analyzer
pip3 install -r requirements.txt
```

## 启动

```bash
python3 app.py
```

浏览器访问 **http://localhost:5050**

## 使用流程

1. **上传**：选择 1~3 个抓包文件（pcap/pcapng），点击「上传并识别」
2. **确认识别结果**：系统显示检测到的服务器 IP、音频/视频流数量，以及**检测到的通话列表**（每通含时间范围、流数、完整性徽章，可展开查看判断依据）
3. **选择分析参数**：多通通话时先**选择通话**（默认选中第一通完整的），再选延迟方向与媒体类型
4. **查看结果**：摘要卡片 → 9 面板图表 → 音视频回放（标注所属通话）→ 详细报告
5. **回放媒体**：在「音视频回放」区按端点分组试听/观看（开头标明本通通话谁打给谁，每条流标注谁到谁），可下载

## 输出目录与清理

生成的音频/视频按**日期**组织，便于定期清理：

```
outputs/
├── 2026-09-11/                  # 按天分目录
│   └── <session_id>/
│       ├── audio/
│       │   ├── seat_outbound_0x1234abcd.wav    # 坐席端发送的音频
│       │   ├── seat_inbound_0x5678ef01.wav     # 坐席端接收的音频
│       │   ├── fs_inbound_0x9abc2345.wav
│       │   └── terminal_inbound_0xdef06789.wav
│       ├── video/
│       │   ├── seat_outbound_0xaaaa1111.mp4    # H.264 → MP4
│       │   └── seat_outbound_0xaaaa1111.h264   # 原始裸流（ffmpeg 失败时保留）
│       └── media_manifest.json   # 媒体清单（含每个流的元信息）
└── chart_xxx.png                 # 分析图表
```

### 清理脚本（crontab 示例）

```bash
# 删除 30 天前的媒体输出（按日期目录名判断）
find outputs/ -maxdepth 1 -type d -name "20[2-9][0-9]-[0-9][0-9]-[0-9][0-9]" -mtime +30 -exec rm -rf {} +

# 同时清理对应的上传文件（按 mtime）
find uploads/ -mindepth 1 -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +
```

> 注意：会话数据存在内存中（`sessions` 字典），重启后丢失。媒体文件在磁盘上，靠上述脚本清理。

## API

| 路由 | 方法 | 说明 |
|---|---|---|
| `/` | GET | 主页 |
| `/api/upload` | POST | 上传抓包（multipart，字段名 seat/fs/terminal），响应含 `calls` 通话列表 |
| `/api/analyze` | POST | 执行分析 `{"session_id", "direction", "media_type", "call_id"?}`；`call_id` 限定分析范围到某通通话，缺省时单通自动选中、多通分析全部 |
| `/api/session/<id>` | GET | 会话信息与结果（含 media_manifest） |
| `/media/<date>/<session_id>/...` | GET | 媒体文件（WAV/MP4） |
| `/charts/<filename>` | GET | 分析图表 PNG |
| `/results/<session_id>` | GET | 独立结果页 |

## 支持的编解码

| 类型 | 编解码 | 重建支持 |
|---|---|---|
| 音频 | G.711 PCMU (PT=0) | ✅ WAV |
| 音频 | G.711 PCMA (PT=8) | ✅ WAV |
| 音频 | GSM / G.722 / G.729 | ❌（页面会提示） |
| 视频 | H.264 (PT=96+) | ✅ MP4（需 ffmpeg）/ H.264 裸流 |

## 已知限制

- **并发通话配对**：多通通话时间上完全重叠时（服务端同时段多通并发），按时间重叠聚类可能错并为一通；顺序通话与端口复用场景已正确拆分
- 时钟偏移：不同抓包机器时钟可能有数百毫秒偏差，跨抓包延迟会自动检测并修正，偏差过大时报告会给出警告
- 视频流按动态 PT（96-127）识别，若实际是 Opus 等动态音频 PT 会被误分为视频
- 重建音频时按 20ms/包 补静音，实际包长不同时会有轻微时长偏差
