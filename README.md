# RTP Stream Analyzer

VoIP 通话 RTP 音视频流分析平台。上传抓包文件（pcap/pcapng），自动检测**通话数量与抓包完整性**，分析**延迟、抖动、丢包**，检测**杂音/啸叫/花屏**类音画异常，并从 RTP 流**重建音频/视频供回放**。

## 功能

### 1. 通话检测与完整性标注
服务端抓包往往同时包含多通通话，分析前先自动分组：
- **通话分组**：按双向端口对构建媒体腿，时间重叠 + 共享 IP 聚类成通话；跨抓包文件按相同 SSRC 合并
- **完整性判断**（每通通话 × 每个抓包文件独立判断，附判断依据）：

| 状态 | 含义 |
|---|---|
| ✅ 完整 | 通话首尾都在抓包内（依据：INVITE 早于媒体开始 / BYE 晚于媒体结束 / 上行流首包 seq≈0） |
| ⚠️ 缺开头 | 开始抓包时通话已在进行（抓到一半） |
| ⚠️ 缺结尾 | 抓包结束时通话尚未挂断 |
| ❌ 首尾都不完整 | 抓包窗口完全落在通话中间 |

- 分析时**按通话过滤**：多通通话时选择具体通话再分析，避免不同通话的延迟/抖动混在一起失真（默认自动选中唯一通话；也可选"全部混合"，页面会提示风险）
- **跨抓包一致性检查（传错文件提醒）**：同一次通话的 SSRC 在每个抓包点相同、会被合并进同一通，因此坐席/FS/终端几份抓包至少应共享一通通话。若某两个角色之间找不到任何共同通话，判定为"可能传错了文件"，上传结果页与结果报告页都会显示黄色提醒（列出每个角色各自检测到的通话），并且此时**不再提供"全部混合"选项**、默认选中覆盖抓包最多的那通，引导用户以其中一通为准单独分析
- 判断依据引用 SIP 信令（INVITE/BYE 时间点）、上行流首包序列号、媒体起止与抓包边界的距离
- **抓包文件完整性提醒（文件级兜底，弹窗确认后继续）**：像 Wireshark 打开抓包时的提示——检测两类文件级问题：**快照截短**（抓包快照长度小于包的真实长度，记录头 orig_len > incl_len，载荷被切掉，对应 Wireshark 的 "Packet size limited during capture"）与**文件尾损坏**（抓包被强制终止或文件传输出错，最后一个记录只剩半截，对应 "…cut off in the middle of a packet"）。上传识别页会列出逐文件明细；点击"开始分析"时**弹窗让用户确认**——"继续分析"按现有数据照常分析（本会话内确认一次后不再重复弹窗），"放弃分析"则留在配置页。确认继续后，结果报告页顶部保留黄色横幅、详细报告的问题清单首位给出数据说明，逐文件列出截短包数、其中 RTP 媒体包数、最多缺失字节数与快照长度（确为快照截短时），提醒"相关统计与媒体重建可能受影响"。截短包的 RTP 头通常完好，延迟/抖动/序号统计仍可信，媒体重建的对应片段会缺内容；完全无法解析的文件在上传时直接返回明确的错误提示（而非 500）
- **信令按 Call-ID 唯一归属**：每个 Call-ID 会话组只挂到时间重叠最大的一通通话，同设备对背靠背的多次通话互不串扰（信令流程与完整性判断——INVITE/BYE 依据——都只看本通话自己的会话）
- **SIP 信令流程时序图（阶梯图）**：每通通话渲染为信令阶梯图，只保留「谁打给谁」的核心对话（识别结果页和结果报告页均可展开查看）；**通话卡片头部同样直接展示「主叫 → FS → 被叫」链路**，与阶梯图列头身份一致
  - 参与方为竖列：**经服务器 = 左（主叫）/ 中（FS 服务器）/ 右（被叫）；点对点呼叫 = 左右两列**。主叫/被叫自动标注徽章（主叫 = 第一个非服务器侧 INVITE 的发送方；被叫 = INVITE 事务 200 OK 的发送方，按 CSeq 归属判定，不受 CANCEL/BYE 的 200 干扰）；并发振铃的分叉目标等无关参与方及其消息不展示
  - **列头显示设备身份**：主叫取其自己 INVITE 的 From（自报账号/显示名），被叫取呼向它的 INVITE 的 To（被叫分机号——被叫响应里的 From 会按 RFC 3261 回显主叫身份，不能用于识别被叫）；无 SIP 身份信息时回退显示 IP，IP 始终保留在副行，长标识悬停可见全文
  - 按 Call-ID 从各抓包中提取 INVITE/ACK/BYE/CANCEL 等会话内消息，跨抓包去重（利用 CSeq 区分重传与认证重试，过滤 REGISTER/OPTIONS 保活噪声）。**多抓包副本按信令源优先级只保留一份**（FS 端 > 终端 > 坐席端）：FS 单一时钟、两侧都可见，整条时间线出自同一台机器，避免多机器时钟偏差导致消息排错序；同一 CSeq 的重传（间隔可达数十秒）也会被去重。**大 SDP 的 IP 分片重组**：带视频编码列表的 SIP 消息常超过 MTU 被 IP 分片（只有首片带 UDP 头，SDP 正文落在后续分片里），解析前先重组，否则这些消息的 SDP（协商编码、媒体端点）全部丢失，直接影响信令流程与通话归属判定
  - 每条消息为带箭头横线，箭头指向接收方，线上标注时间与消息类型，按类型着色：请求=蓝、1xx=灰、2xx=绿、3xx~6xx=红
  - **RTP 媒体区间标线（接通后）**：两条标线**锚定在信令行上**——绿色开始线紧跟被叫应答的 200 OK 行之后，灰色结束线落在首条 BYE 行之前，保证两条线之间不夹应答/挂断握手的其余信令；线上标注媒体起止时间与持续时长。FS 从主叫一呼叫就可能开始收录 RTP（含振铃音/早期媒体），时间标注专指**双方接通后真正交换媒体**的区间（answer→bye 窗口内的 RTP 首末包）；无信令时回退为整段媒体首末包
  - **编码标签**：开始线下方（RTP 区间内）显示该通话实际使用的音频/视频编码——由 RTP 流真实出现的载荷类型（PT）反查：静态 PT（如 0=PCMU）用内置名称，动态 PT（96~127，如 H264）用 SDP rtpmap 解析；DTMF 事件流（telephone-event）不算媒体编码；动态 PT 连 SDP 都未抓到时标注 PT 号并说明
  - **FS 参与编解码判定**：协商结果按腿分行、按信令时序落位——「被叫侧协商」行紧跟该腿应答（200 OK）之后、「主叫侧协商」行紧跟 FS 对主叫的应答之后（每条腿各协商了什么编码，在图上出现的时刻不早于该腿自己的应答），转码判定行固定在 **RTP 媒体开始标线之前**——两腿协商全部结束、呼叫接通之后才给结论，展示顺序与真实协商时序一致。折叠标题同步显示「主叫 … / 被叫 …」。FS 作为 B2BUA，一条通话有两条腿（主叫↔FS、FS↔被叫）各带独立的 SDP 协商，按 Call-ID 分别配对每条腿的 offer（INVITE）与 answer（200 OK），取交集得到该腿协商编码（编码同名但时钟率不同视为不同编码，如 OPUS/48000 ≠ OPUS/16000；FS 自身 INVITE 常用不带 rtpmap 的静态 PT，按 RFC 3551 内置时钟率表补全后参与比较），再对比两条腿得出判定——**FS 参与转码**（两腿编码不同，红色徽章，注明两侧编码）/ **FS 未转码**（两腿编码相同，绿色徽章；注：同编码下 FS 是否透明重编码无法从 SDP 区分）/ **媒体不经 FS**（点对点直连，FS 不在媒体路径）/ **无法判定**（只抓到单腿 SDP 时诚实标注）。信令里完全没有 SDP 时退化为按 RTP 载荷类型推断并注明"依 RTP 载荷类型推断"。通话卡片头部、通话切换按钮、下拉选择器同步显示转码徽章
  - 可直观还原呼叫过程：应答、407 认证重试、re-INVITE、挂断双向 BYE 等
  - **FS 媒体转发判定（是否 bypass 中转）**：明确提示"音视频流到底有没有经过 FS 转发"，并按排查优先级给出方向——**中转问题优先，网络问题其次**。信令判据是 SDP 透传改道：FS 发出的消息里宣告的媒体端点是对端设备的地址（而非 FS 自己），说明 FS 把另一条腿的 SDP 原样透传了（bypass_media_after_bridge 等场景），媒体改道为端到端直连——阶梯图上这些消息带「媒体改道」标记，通话卡片头部显示「已改道」徽章，提示块列出改道时刻、消息与被宣告的媒体地址。实测判据是各设备与 FS 之间的 RTP 上/下行：**两端都没有上行 = 优先排查中转配置**（bypass media、信令里媒体地址是否指向 FS），**只有部分端上行 = 才考虑网络问题**（先在未发送端本地抓包排除终端自身不发，再查链路/防火墙/NAT）；两端都有上下行 = 转发正常。附加证据链：改道时刻各端上行的"信令性停止"（±5 秒内齐停 = 服从了新 SDP，不是丢包形态）、FS 有下行但对端从未上行（该下行是 FS 本地媒体源——彩铃/视频公告/MOH——并非转发）、下行包数远超对端上行包数（转发包数应约 1:1）。结论同时写入结果报告：改道/无上行记 critical 问题、部分上行记 warning、转发正常记 ok 项。仅当抓包点含 FS 侧抓包时才实测判定，否则诚实提示"无法判断"

### 2. 延迟 / 抖动 / 丢包分析
- **FS 内部处理延迟**：在 FS 抓包中匹配入站/出站 SSRC 对，测量转发耗时
- **跨抓包传输延迟**：同一 SSRC 在不同抓包点的到达时间差（自动修正抓包机器间的时钟偏移）
- **端到端延迟估算**：FS 延迟 + 网络传输
- **抖动分析**：包间隔稳定性（均值/中位数/标准差/P95/P99/异常间隔）
- **丢包检测**：基于 RTP 序列号连续性
- 生成 9 面板分析图表 + 结构化结论报告（含问题分级与根因建议）

### 3. 音视频重建与回放
- **音频**：从 RTP 载荷重建 G.711 PCMU（μ-law）/ PCMA（A-law）为 WAV 文件
  - 按序列号排序，丢包位置自动补静音
  - 按抓包文件（坐席/FS/终端）分组，区分**呼出（该端发送）**与**呼入（该端接收）**
  - 每条流标注**收发双方（谁到谁）**：从通话 SIP 信令识别主叫/被叫（分机号/显示名），结合流的实际收发 IP 生成「主叫 张三（1001）→ FS」式标注；无信令时退化为抓包角色名或 IP。回放区开头附一句通话拓扑（主叫 ↔ FS ↔ 被叫，含 IP）
- **视频**：H.264 流去分片（FU-A/STAP-A，RFC 6184）导出裸流，调用 ffmpeg 转换为 MP4
- 网页内直接播放 / 下载

### 4. 音画质量异常分析（杂音 / 啸叫 / 花屏）
针对"有杂音、啸叫、画面花"类投诉，对重建的媒体做针对性检测（`quality_analyzer.py`），结果进入详细报告的「音画质量分析」区块与结论问题清单，事件时间均相对该流开始（可与回放页对听）：

**音频**（G.711 PCMU/PCMA 解码后做 DSP，其他编码诚实标注"不可解"）：

| 检测项 | 原理 | 听感对应 |
|---|---|---|
| 啸叫/持续单频音 | 帧级 FFT 找"又高又窄又稳定"的谱峰（峰值/谱中位数 ≥40 倍、持续 ≥0.26s、频率不漂移），并做谐波伙伴检查（2f/3f/f÷2 处有显著峰 → 判为语音谐波，不误报） | 通话中的尖啸声（扬声器回授）、单音提示音串入 |
| 低频嗡声 | 低频段（≤220Hz）能量占比 ≥85% 且持续 ≥0.8s | 50/100Hz 电源干扰、接地环路、风扇声 |
| 削波破音 | 波形顶端被削平：连续 ≥4 个相等的大幅值采样 | 沙哑、噼啪的破音（发话端音量过大） |
| 爆点/咔哒声 | 孤立脉冲短突发（幅度极大、外围邻域都很小） | 突发电气干扰、线路接触不良 |
| 底噪 | 静音帧电平中位数 > -45 dBFS 报偏高 | 持续的沙沙/电流声 |
| 音量 | 话音帧平均电平过低（< -27 dBFS）或接近满幅 | 声音小、发虚 / 易破音 |

**视频**（RTP 层证据，H.264）：
- **丢包 → 花屏映射**：视频丢包会花到下一个关键帧（IDR）才恢复，把每次丢包事件映射为"距下一 IDR 的时长"，估算累计花屏影响时间（少量视频丢包的听感几乎无感、观感明显，报告里会说明差异）
- **破损 NAL 计数**：FU-A 分片中段丢包/未收尾/首片丢失、STAP-A 内部不完整——拼出的帧数据必然损坏，是"解码一定出错"的直接证据
- **关键帧间隔**：全程无 IDR（丢包后无法自愈，花屏持续到挂断）或间隔 >10s（每次丢包后花屏持续过久）都会提示
- **ffmpeg 解码校验**（有重建裸流且装了 ffmpeg 时）：对裸流跑错误级解码并统计错误行数，作为花屏风险的最终佐证

摘要卡片同步显示「音画质量：正常 / 有异常」。

### 4.1 声音问题分类（对照《声音问题种类》清单）

针对"听感类"投诉，把上面各检测器的结论按根目录《声音问题种类.md》清单**聚合分类**（`problem_taxonomy.py`），在详细报告的「声音问题分类」区块输出面向用户的分类卡片。每类问题包含：

- **优先级**（P0 无声/单通 → P3 轻微音质）与**类别**（无声/连通、失真、断续、噪声、回声、音量、网络、协议/时钟、设备/编解码）
- **用户听感词**：清单"用户常说"列的原话（如"我听不到对方""电音、机关枪""声音发闷"）
- **种类描述**：该问题在抓包层意味着什么
- **证据**：命中该分类的各检测器结论（多检测器命中同一类时合并为多条证据，如丢包同时被序号缺口与 RTCP RR 自报发现）
- **排查方向 / 验证方法**：清单"常见原因"与"验证方法"两列

映射关系：无声诊断 blocked/silent → 单通 P0；FS 转发改道/部分上行 → 单通；序号缺口 + RTCP 自报丢包 → 丢包失真（电音/机关枪/吞字）；时间戳大段跳变 → 断音/内容缺失；时间戳倒退 → 时钟异常（变调/忽快忽慢）；时间戳重复 → 重复音；啸叫 → P1；削波 → 失真破音；低频嗡声 → 电流声；爆点 → 瞬态咔哒；底噪偏高 → 底噪；电平过低/过高 → 音量；FS 延迟/抖动/链路偏高 → 延迟抖动；G.711 窄带 → info 级"发闷/水声"编码特性说明（不计入问题数）。

**诚实边界**：风噪、喷麦、齿音、接触不良、侧音回声、双讲压制等声学/设备侧现象抓包层面无法确认，区块底部以折叠表列出这 8 类问题的原因与**人工验证方法**（来自清单"验证方法"列），避免"没报出来 = 没问题"的误导。

### 5. 自适应抓包数量与分析内容选择
支持上传 1~3 个抓包文件（坐席端 / FS 端 / 终端端任意组合），系统自动识别可用分析项：

| 上传组合 | 可用分析 |
|---|---|
| 单端 | 抖动 + 丢包（延迟测量自动禁用） |
| 坐席 + FS | 坐席↔FS 传输延迟 + FS 内部延迟 |
| FS + 终端 | FS↔终端 传输延迟 + FS 内部延迟 |
| 三端齐全 | 端到端延迟 + 全部分析项 |

「选择分析参数」页可勾选**分析内容**：**延迟测量**（FS 内部 / 跨抓包 / 端到端；仅单端抓包时自动禁用——延迟需要 ≥2 个抓包点或含 FS 抓包才可测，抖动/丢包不受影响）与**音画质量**（杂音 / 啸叫 / 花屏，单端抓包即可分析）；**媒体类型**（仅音频 / 仅视频 / 都分析）同时限定延迟与音画质量两类分析的作用范围。

## 环境要求

- Python 3.8+（开发环境为 3.11）
- **ffmpeg**（可选，视频转 MP4 需要）：`brew install ffmpeg`
- 其余依赖见 `requirements.txt`

## 安装

```bash
cd rtp-stream-analyzer
pip3 install -r requirements.txt
```

## 启动

```bash
python3 app.py
```

浏览器访问 **http://localhost:5050**

outputs 目录（分析图表与音视频文件）由后台线程自动清理：默认保留 2 小时、每 10 分钟巡检一次，可在 `app.py` 顶部的 `OUTPUT_RETENTION_HOURS` / `OUTPUT_CLEANUP_INTERVAL_MINUTES` 配置项调整。

## 使用流程

1. **上传**：选择 1~3 个抓包文件（pcap/pcapng），点击「上传并识别」
2. **确认识别结果**：系统显示检测到的服务器 IP、音频/视频流数量，以及**检测到的通话列表**（每通含时间范围、流数、完整性徽章，可展开查看判断依据）
3. **选择分析参数**：多通通话时先**选择通话**（默认选中第一通完整的），再选延迟方向与媒体类型
4. **查看结果**：摘要卡片 → 9 面板图表 → 音视频回放（标注所属通话）→ 详细报告
5. **回放媒体**：在「音视频回放」区按端点分组试听/观看（开头标明本通通话谁打给谁，每条流标注谁到谁），可下载

## 输出目录与清理

生成的音频/视频按**日期**组织，便于定期清理：

```
outputs/
├── 2026-09-11/                  # 按天分目录
│   └── <session_id>/
│       ├── audio/
│       │   ├── seat_outbound_0x1234abcd.wav    # 坐席端发送的音频
│       │   ├── seat_inbound_0x5678ef01.wav     # 坐席端接收的音频
│       │   ├── fs_inbound_0x9abc2345.wav
│       │   └── terminal_inbound_0xdef06789.wav
│       ├── video/
│       │   ├── seat_outbound_0xaaaa1111.mp4    # H.264 → MP4
│       │   └── seat_outbound_0xaaaa1111.h264   # 原始裸流（ffmpeg 失败时保留）
│       └── media_manifest.json   # 媒体清单（含每个流的元信息）
└── chart_xxx.png                 # 分析图表
```

### 自动清理

outputs 目录（图表 + 媒体文件）与 uploads 目录（上传的抓包文件）由应用内置的后台线程自动清理：默认保留 2 小时、每 10 分钟巡检一次，应用启动时也会先清一次历史遗留。两处共用同一保留时长，可在 `app.py` 顶部调整 `FILE_RETENTION_HOURS` / `FILE_CLEANUP_INTERVAL_MINUTES` 两个配置项。

> 注意：会话数据存在内存中（`sessions` 字典），重启后丢失。超过保留时长后，旧结果页的媒体/图表链接会失效，对旧会话重新分析也会因原始抓包已被清理而失败——这是保留时长的预期行为，需要更长保留就调大配置项。

## API

| 路由 | 方法 | 说明 |
|---|---|---|
| `/` | GET | 主页 |
| `/api/upload` | POST | 上传抓包（multipart，字段名 seat/fs/terminal），响应含 `calls` 通话列表 |
| `/api/analyze` | POST | 执行分析 `{"session_id", "direction", "media_type", "call_id"?}`；`call_id` 限定分析范围到某通通话，缺省时单通自动选中、多通分析全部 |
| `/api/session/<id>` | GET | 会话信息与结果（含 media_manifest） |
| `/media/<date>/<session_id>/...` | GET | 媒体文件（WAV/MP4） |
| `/charts/<filename>` | GET | 分析图表 PNG |
| `/results/<session_id>` | GET | 独立结果页 |

## 支持的编解码

| 类型 | 编解码 | 重建支持 |
|---|---|---|
| 音频 | G.711 PCMU (PT=0) | ✅ WAV |
| 音频 | G.711 PCMA (PT=8) | ✅ WAV |
| 音频 | GSM / G.722 / G.729 | ❌（页面会提示） |
| 视频 | H.264 (PT=96+) | ✅ MP4（需 ffmpeg）/ H.264 裸流 |

## 已知限制

- **并发通话配对**：多通通话时间上完全重叠时（服务端同时段多通并发），按时间重叠聚类可能错并为一通；顺序通话与端口复用场景已正确拆分
- 时钟偏移：不同抓包机器时钟可能有数百毫秒偏差，跨抓包延迟会自动检测并修正，偏差过大时报告会给出警告
- 视频流按动态 PT（96-127）识别，若实际是 Opus 等动态音频 PT 会被误分为视频
- 重建音频时按 20ms/包 补静音，实际包长不同时会有轻微时长偏差
